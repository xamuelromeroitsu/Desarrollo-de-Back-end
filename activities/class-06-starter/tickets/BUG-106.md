# BUG-106 — Empty filtered collection answers 404

Reported by: support team
Severity: medium
Status: closed

## Symptom

When a valid collection filter has no matches, `GET /requests` returns `404`.

Steps to reproduce (with the workshop seed):

1. Log in as `ana.requester.seed@example.test`.
2. Request `GET /requests?status=closed` with her token.
3. Observe the response.

Ana has no closed requests, so the filter is valid and matches nothing.

## Expected behavior

A valid collection with no matches must return:

```http
200 OK
```

```json
[]
```

An empty collection is NOT a missing resource. `404` is for an individual
resource that does not exist (or must not be revealed) — see the class 3
contract for collections.

## Definition of done

1. `GET /requests?status=closed` (as Ana) answers `200` with `[]`.
2. The rest of the suite still passes.
3. A regression test pins the behavior so it cannot silently come back.

---

## 🔍 Diagnóstico (root cause)

El origen está en **`src/modules/requests/requests.service.js:75-79`**.

### Las líneas del código y su explicación

```js
const rows = await findAll(scope);          // 1) busca las solicitudes según el filtro
if (rows.length === 0) {                    // 2) "¿no encontró nada?"
  throw new AppError('resource',            // 3) si el array está vacío → LANZA ERROR
    'REQUEST_NOT_FOUND',
    'No requests matched the given filters.');
}
return rows.map(mapRequestRow);             // 4) si hay filas → las devuelve
```

1. `findAll(scope)` le pregunta a la base de datos: "dame las solicitudes que coincidan"
   (en este caso: `status = closed` y `created_by = [usuario]`). Devuelve un **array**.
2. `rows.length === 0` significa "no hay coincidencias".
3. Ese `throw` crea un `AppError('resource', 'REQUEST_NOT_FOUND', …)` que luego
   `src/http/respond-error.js` traduce a **HTTP 404**.
4. Solo si hay filas llega el `return` con la lista. La colección vacía nunca llega a devolverse.

### Por qué es un bug

- **Estante vacío** (colección sin coincidencias de un filtro válido) → respuesta normal: `200 + []`.
  No está roto, está vacío.
- **Bizcocho que no existe** (un recurso individual `GET /requests/99`) → ahí sí es `404`
  (lo cubre `getRequest`, `requests.service.js:83-90`, que NO se modifica).

El `if` confunde la colección vacía con el recurso inexistente.

## 🔄 Antes y después del fix

| `rows` | ANTES (actual) | DESPUÉS (fix) |
| --- | --- | --- |
| `rows = []` | `if` → `throw` → **404** ❌ | sin `if` → `return rows.map(...)` → **200 `[]`** ✅ |
| `rows = [una, dos]` | `200 + [...]` (bien) | **Igual**, no cambia nada ✅ |

### Cambio mínimo aplicado en `requests.service.js`

Se elimina el bloque de las líneas 76-79 y queda:

```js
const rows = await findAll(scope);
return rows.map(mapRequestRow);
```

## 🧪 Prueba de regresión

Añadida en `test/requests.test.js`:
`returns an empty array when a valid filter has no matches` — usuario recién creado (no seed),
`GET /requests?status=closed` con su token, espera **`200` + `assert.deepEqual(response.body, [])`**.

- **Rojo 🟥** (previo al fix): esperado `200 + []` → obtenido `404`.
- **Verde 🟩** (con el fix): todos los casos pasan (`tests pass, fail 0`).

## 🧭 Paso a paso: el flujo de archivos y los errores

```
test/requests.test.js          (la prueba dispara la petición con supertest)
        │
        ▼

        │  express.json()
        ▼

        │
        ▼

        │
        ▼

        │   ← aquí está el bug: líneas 75-79 lanzan el error
```

### 2) Dónde aparece el error y quién lo convierte a 404

| Paso | Archivo | Qué ocurre | Qué sale |
| --- | --- | --- | --- |
| 1 | `requests.routes.js:18-25` | invoca `listRequests` | — |
| 2 | `requests.service.js:75-79` | `rows.length === 0` → **lanzar AppError** | `AppError('resource', 'REQUEST_NOT_FOUND')` |
| 3 | `requests.store.js:19-47` | `findAll` ejecuta el `SELECT` | `[]` (perfecto, pero no se usa) |
| 4 | `respond-error.js` | mapea categoría `resource` | **HTTP 404** ❌ |

> El error NO nace en el store (devuelve `[]` bien) ni en la ruta (pidió `200`).
> Nace en el **service**, que decidió convertir "0 filas" en excepción.

## 📌 Resumen

El `if` sobrante es el bug: preguntaba "¿está vacío?" y respondía "error", cuando debía responder
"aquí está: `[]`". Solo se eliminó ese bloque; la validación de filtros (`400 INVALID_FILTER`),
los permisos y el `404` de `getRequest` se mantienen intactos.
